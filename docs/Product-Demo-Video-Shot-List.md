Status

This is the production shot list only. It does not modify `docs/Product-Demo-Video-Storyboard.md` — that document remains the single source of truth for narrative, structure, timing and scenes. This document translates each of its 13 scenes into a filmable production block: what already exists, what's missing, and exactly what to do with a camera/recorder pointed at a screen.

Every fact below was checked against this repository — real committed screenshots (`public/product-screens/screen-01.png` → `screen-29.png`), the live routes in `src/routes/`, `src/components/marketing/content.ts`, `src/components/site/ProductMock.tsx`, and `scripts/prepare-marketing-screens.mjs` (the tool that produces the `mkt-*.webp` marketing crops from those real screenshots). Nothing below is invented. Where the real product's actual behaviour differs from the storyboard's shorthand description, or where a screen genuinely doesn't exist yet, it's flagged with a blocker code (B1–B5) rather than guessed at — see the key below the table.

Blocker key

- **B1 — Feature does not exist.** Confirmed absent from every real screenshot's navigation (Home / Work / Inventory / Insights / Planning / Settings). Genuine product-build gap.
- **B2 — No recordable instance.** The feature is real and shipped (proven by a real screenshot), but no interactive, recordable version of it exists in an accessible codebase. Only two screens in this repo are actually live and interactive: `/dashboard` and `/rfq-comparison`. Everything else is a single static crop. This is an access/build-a-demo problem, not a missing feature.
- **B3 — Interaction mismatch.** The storyboard's shorthand description of the interaction doesn't match how the real screen actually behaves. Noted so nobody tries to film a control that doesn't exist.
- **B4 — PII in reference captures.** The real screenshots on file contain what appear to be genuine personal email addresses (e.g. `aurimasdarguziz@gmail.com`, `ingrid.really@gmail.com`). Any seeded account used for actual filming must be scrubbed of this before recording.
- **B5 — No single screen matches the claim.** The real product currently splits "spend, usage and savings" across three separate report pages (Savings & Usage, Stock Reports, Orders Reports) plus the Dashboard KPI row — not one combined view.

Notable positive finding (N1): `src/routes/rfq-comparison.tsx` in this repo is already a fully built, live, interactive page — side-by-side supplier columns, click-to-select, running totals, "Generate purchase order." It already contains **"Lidocaine 2% with epinephrine cartridges"** as one of its five mock products — i.e., the storyboard's throughline product already exists in a ready-to-record page in this codebase. This is a different (better, and already-brand-aligned) source than the storyboard's `SCREENS.rfqCompare` / `mkt-rfq-workflow.webp`, which is a static image stitched from three separate captures of the real product's different, per-item quote-entry screen. Recommend recording Scene 8 from `/rfq-comparison`, not from the real product.

(N2): `/dashboard` in this repo is likewise a live, interactive recreation, matching Scenes 4 and 12. Recording from it directly (rather than the static `mkt-dashboard.webp` crop) avoids re-cropping browser chrome and gives full control of resolution.

### Production blockers

Ordered by priority — highest-impact / hardest-to-unblock first.

1. **Scene 10 — Invoice mismatch (B1).** The single hard product blocker in this list. No Invoice nav item, page, or modal exists anywhere in the real product (checked against all 29 real screenshots and every visible sidebar). This is a genuine design-then-build gap, not a filming problem. Nothing about this scene — not even its exact visual layout — can be pinned down further until product decides what an Invoice Matching screen looks like. Every other scene in this list can, in principle, be filmed without touching engineering; this one can't.
2. **Scenes 5, 6, 7, 9, 11 — no recordable instance (B2).** These five real, shipped features have zero interactive, recordable presence in any codebase this document has access to. Only `/dashboard` and `/rfq-comparison` in this repo are actually live pages — every other "screen" in the storyboard is a single static image. Filming the hover/click/scroll motion the storyboard describes requires either (a) recording access to a seeded `app.reacting.io` account, or (b) building interactive marketing-demo recreations the same way `/dashboard` and `/rfq-comparison` were already built. This blocks five of the eleven screen-based scenes and is the single highest-leverage unblock available — resolving it (most likely option (a), since it needs no new code) clears most of the shot list at once.
3. **Scene 11 — no single screen matches the VO claim (B5).** Independent of the access blocker above, there's an open production decision: "spend, usage and savings are already sitting there" implies one view, but the real product splits this across three report pages. Needs a decision before this scene can be filmed even once access exists.
4. **PII in every real reference capture (B4).** `aurimasdarguziz@gmail.com` and `ingrid.really@gmail.com` (and similar) appear as contact/creator emails across the stock, vendor, purchase order and delivery screenshots on file. Whatever account is used for actual filming must be freshly seeded and scrubbed — the existing reference captures must not be the ones filmed from, or re-used as B-roll, without this being fixed first.
5. **Interaction mismatches (B3) on Scenes 5, 6, 9.** Minor relative to the above, but worth fixing before a shoot day rather than during one: the storyboard's "hover reveals," "clicks through," and "flags as short" language doesn't literally match the real controls (click-to-open, single-button "Add to RFQ," and a Follow-up-qty field, respectively). Not a reason to change the storyboard's narrative — just a heads-up so the person operating the cursor on the day isn't looking for a control that isn't there.

### Recording order

Not the playback order — the order that minimises setup switches and keeps demo data consistent.

1. **Motion graphics / VO-only scenes (1, 2, 3, 13)** — no product dependency at all. Can be produced in parallel with everything else, any time, by the design/VO team alone.
2. **Scene 8 (`/rfq-comparison`)** — ready now, needs no seeded backend, no external access, and no other scene's state to be true first. Record this first among the screen-based scenes, and budget the most retakes here per the storyboard's own note.
3. **Scenes 4 and 12 (Dashboard)** — also ready now (static hold, either from the live `/dashboard` route or a fresh capture). No dependency on the other scenes, but if picture-perfect continuity is wanted (KPI numbers reflecting the resolved invoice mismatch), reshoot Scene 12's plate last, after Scene 10 exists.
4. **Scenes 5 → 6 → 7 → 9 → 11, in that exact order, in one continuous session against one seeded account.** These are stateful: the anaesthetic-cartridges item must actually be low before it can be actioned toward a quote, actually ordered before it can be received, and actually received (with a shortfall) before reporting can reflect it. Recording them out of story order risks the demo data not lining up on camera. This is the block that's currently unable to start (blocker #2 above).
5. **Scene 10 (Invoice mismatch) — last, and only once built.** Once the feature exists, it must be slotted into the same continuous session as step 4, between Delivery (9) and Reporting (11), so the same order and the same delivery shortfall carry through to the invoice and then to the numbers in Scene 11.

### Assets still required

Only what's genuinely missing — not implementation tasks.

- **An Invoice Matching screen of any kind.** Doesn't exist as a shipped page, a design mock, or even a rough wireframe anywhere in this repo or the real captures on file (Scene 10).
- **Recording access to a seeded, resettable `app.reacting.io` account** (or an interactive recreation, as already exists for `/dashboard` and `/rfq-comparison`) that contains the anaesthetic-cartridges item moving through Stock → Low Stock → Vendor → Order → Delivery → Reporting, so Scenes 5, 6, 7, 9 and 11 can be recorded at all.
- **A production decision on which real screen(s) represent Scene 11's "spend, usage and savings" claim** — Savings & Usage, Stock Reports, Orders Reports, or the Dashboard KPI row. Currently undecided and unfilmable as literally described.
- **Sanitised demo data.** The real captures on file expose what look like genuine personal email addresses. A clean seeded account (no real names, no real emails) is required before any of this is filmed for public release, not just before it's published.
- **The original, full-resolution source captures for Stock, Low Stock, Expiring Stock and Purchase Orders.** Per `scripts/prepare-marketing-screens.mjs`, these currently live only on a developer's local machine (`Desktop/New reacting/app images`), not in this repository. If a different crop, angle, or a higher-resolution source is ever needed for the video (rather than a fresh screen recording), that source will need to be re-supplied — it isn't retrievable from this codebase today.
